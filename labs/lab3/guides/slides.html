Wildcards and links

Two ideas: the shell turns patterns into names, and one file can have more than one name.

Lab 3

A wildcard is a pattern, and the shell expands it

  • A wildcard is a character that stands for other characters, such as * for any characters.
  • The shell, not the command, expands the pattern into a list of matching names, then runs the command with that list.
  • If nothing matches, Bash keeps the pattern as typed. The command then looks for a file with that exact name.
  • Wildcards select file names. They are not the same as regular expressions.

BEFORE THE LAB

Why learn it here?

One pattern replaces a long list of names. The same pattern, used carelessly with rm, removes more than you meant.

See what the shell really passes

$ printf 'one\n' > practice/report1.txt

$ printf 'two\n' > practice/report2.txt

printf prints each word it receives between angle brackets, one per line.

Without quotes, the shell sends two words: the two .txt files. With single quotes around the whole pattern, it sends one word with a literal *.

Use this trick to check a pattern before you give it to cp, mv or rm.

Concepts first

8

Brackets and braces are not the same

Square brackets look at files

student@server: ~/oslab-work/lab3

$ ls practice/report[12].txt

practice/report1.txt  practice/report2.txt

$ ls practice/report[13].txt

ls: cannot access 'practice/report3.txt': No such file

Only names that exist can match. Bash keeps a pattern with no match, so the error names the pattern.

Braces only write words

student@server: ~/oslab-work/lab3

$ echo practice/report{1,3}.txt

practice/report1.txt practice/report3.txt

The file report3.txt does not exist, and echo does not care. Brace expansion happens first, and no file is looked at.

Concepts first

9

A name is not the file

  • The data of a file lives on the disk. An inode is the record that describes it: size, owner, permissions and where the data is.
  • Every inode has a number. A file name is only an entry in a directory that points to an inode number.
  • Two entries can point to the same inode. They are two names for one file: hard links.
  • The data is freed only when the last name is gone.

inode number, permissions, link count, ...

$ ls -li

12345 -rw-r--r-- 2 student student 4 report1.txt

12345 -rw-r--r-- 2 student student 4 hard-demo.txt

99001 lrwxrwxrwx 1 student student 11 soft-demo.txt -> report1.txt

The 2 in the third column is the link count: two names point to inode 12345. The symbolic link has its own inode, 99001.

Concepts first

13

A relative target is read from the link's folder

student@server: ~/oslab-work/lab3

$ cd ~/oslab-work/lab3

$ ls -l links

lrwxrwxrwx 1 student student 11 soft.txt -> source.txt

 

$ cat links/soft.txt

version 1

$ cd links && cat soft.txt

version 1

The stored target source.txt has no / at the front, so it is relative.

It is resolved from the folder that holds the link (links/), not from the folder where you are standing.

That is why the same link works from two places. Write the target as if you were standing next to the link.

Concepts first

14

The key experiment

student@server: ~/oslab-work/lab3

$ echo 'config data' > original.txt

$ ln original.txt hardlink.txt

$ ln -s original.txt symlink.txt

$ ls -li

$ rm original.txt

$ cat hardlink.txt

config data

$ cat symlink.txt

cat: symlink.txt: No such file or directory

echo with > writes the text into a new file. rm removes only the name original.txt.

The data still has one name, hardlink.txt, so it survives.

symlink.txt still says original.txt, and no such name exists. The link is dangling.

In practice: ls -la /usr/bin/python* shows programs that are managed with symbolic links.

Step 3: repair only the symbolic link

What to do

  1. Look at the old link first: readlink soft.txt.
  2. Remove only that owned symbolic-link entry.
  3. Create it again with ln -s, and choose a relative target yourself.

Internal links are fine

Escaping links are refused

How a program finds its libraries

1. The kernel loads the program

an ELF file

2. The dynamic linker starts

ld-linux.so

3. It finds each .so

LD_LIBRARY_PATH, /etc/ld.so.cache, then /lib and /usr/lib

4. It maps them in

into the process, and the program runs

52

Looking at shared libraries, and building one

student@server: ~/oslab-work/lab3

$ ldd /bin/ls

$ ldconfig -p | grep libc

$ gcc -fPIC -c mylib.c -o mylib.o

$ gcc -shared -o libmylib.so mylib.o

$ gcc main.c -L. -lmylib -o myprogram

$ LD_LIBRARY_PATH=. ./myprogram

ldd lists the libraries a program needs. ldconfig -p searches the library cache.

-fPIC makes position-independent code, so the library can load at any address. -shared makes the .so file.

For a user-local library, set LD_LIBRARY_PATH instead of installing into system folders.

More ways to look at a library

student@server: ~/oslab-work/lab3
