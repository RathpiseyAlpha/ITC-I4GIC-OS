Compare the five approaches

Read these alongside the scenarios above. Peterson is a software protocol; test-and-set and compare-and-swap are atomic building blocks; atomic increment is one complete update; a mutex is a library tool for protecting a whole section of code. They meet different needs, so there is no single replacement order.

Peterson's solution
Flow: raise my flag → give the other thread the turn → wait while it wants in and has the turn → update the counter → lower my flag.
Guarantees: mutual exclusion, progress and bounded waiting in the ideal two-thread model.
Drawbacks: this version handles only two threads and uses busy waiting. Its proof assumes atomic shared accesses with the required ordering; ordinary shared variables in C or C++ are insufficient on real hardware.
Why another approach? Hardware atomics support practical locks for more threads; a blocking mutex addresses prolonged spinning. Neither change automatically preserves Peterson's bounded-waiting guarantee.
Test-and-set spinlock
Flow: atomically read the old lock and set it to 1 → enter if the old value was 0, otherwise retry → update the counter → release the lock.
Guarantees: mutual exclusion and progress, assuming the owner eventually releases the lock and runnable threads keep taking steps.
Drawbacks: retries consume CPU time; bounded waiting is not guaranteed, so a thread may starve.
Why another approach? Use a blocking mutex when waiting is long. Fairness requires an explicit turn-taking or queueing policy; simply replacing test-and-set with CAS does not provide it.
Compare-and-swap (CAS)
Flow here: atomically compare the lock with 0 and replace it with 1 only on a match → retry on failure → update the counter → release the lock.
Guarantees here: the same mutual exclusion and progress as the test-and-set spinlock, under the same scheduling and release assumptions.
Drawbacks: this CAS lock still spins and does not guarantee bounded waiting. In a general CAS update loop, concurrent changes can force repeated retries.
Why use CAS? It can replace a value only if it still matches an expected value, making it useful beyond boolean locks. A CAS instruction alone does not make an entire algorithm lock-free. For a simple increment, fetch_add(1) expresses the job directly.
Atomic increment
Flow: read the counter into a local variable, then try to replace that value with its successor using CAS. If the value changed, read it again and retry. The slide also shows fetch_add(1) as a library operation.
Guarantee: increments of this counter do not lose updates. There is no lock admission protocol to assess for mutual exclusion or bounded waiting.
Drawbacks: one atomic increment does not protect a separate check, several variables or a whole business operation. Even if counter is atomic, a separate load followed by a store is not one atomic increment. A real atomic operation may use hardware, a retry loop or an internal lock; atomic does not always mean lock-free.
Why another approach? Use a mutex for a sequence such as checking stock, reducing it and recording the sale in shared memory. For shared database data, use a suitable transaction.
Mutex lock
Flow here: acquire the mutex, waiting if another thread owns it → perform the entire read, add and write sequence → release it.
Guarantee: one owner at a time, provided every access to the protected data follows the same locking rule. The scenario models a blocking mutex; real implementations may spin briefly before sleeping.
Drawbacks: waiting and waking can add overhead. A missing release can stop progress; inconsistent ordering of multiple locks can deadlock. Ordinary mutex APIs need not guarantee bounded waiting, and a mutex in one server's memory does not protect another server.
Why another approach? For just one counter update, an atomic increment can avoid an explicit critical-section lock. For very short waits, spinning may be useful. Correct lock ordering and reliable release address misuse; no single replacement removes every tradeoff.

Which limitation leads to which idea?

A separate lock test and assignment can race. Combine them in one atomic operation: test-and-set or CAS.
Spinning wastes CPU during a long wait. A blocking mutex lets the thread wait without a user-code spin loop. Switching from test-and-set to a basic CAS spinlock does not solve this.
Only one counter needs incrementing. Use an atomic increment. If several actions must stay together, protect the whole sequence instead.
A thread must not be overtaken indefinitely. Look for a proven fairness policy, such as a ticket or queue lock. Peterson demonstrates bounded waiting for two threads under its assumptions; the simple hardware locks here and an unspecified mutex do not promise it.

The simulator checks finite schedules with program-order execution. It does not simulate real CPU cost, memory reordering, operating-system wakeups or infinite starvation. The drawbacks above explain limits that a successful counter run cannot reveal.
